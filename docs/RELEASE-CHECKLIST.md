# 发布包说明与验收清单

本清单是每个 Clawd 版本包的发布门槛。维护者必须先完成对应版本的变更说明，再生成、标记或上传安装包。只更新程序版本号或只上传二进制文件不算完成发布。

## 每个版本必须具备

- `package.json` 中的 SemVer 版本、Git tag、Release 标题、资产文件名与版本说明文件名一致。
- `docs/RELEASE-NOTES-vX.Y.Z.md`，并在 `CHANGELOG.md` 建立同版本条目。
- 逐项列出面向用户的**新增、调整、修复、安全变化**；无内容的类别应明确写“无”，不得用空泛宣传语代替。
- 说明基线版本、配置/数据迁移、向后兼容情况、安装或手动更新步骤、回退方式与潜在破坏性变化。
- 按目标平台逐个列出交付文件、类型、大小和 SHA-256；区分安装包、Codex 宠物包、壁纸及其他附件。
- portable 发布命令必须把 Codex ZIP 与浅/深 4K 壁纸汇集到发行目录，生成 `release-manifest-vX.Y.Z.json`，记录精确 40 位源码 commit、构建平台、资产文件名、字节数与 SHA-256；manifest 和每个发布附件都必须进入 `SHA256SUMS.txt`，manifest 随包上传。
- 记录验证项目、结果、执行环境、精确源码 SHA 和 CI 结论；明确区分本地自动化、CI、人工设备验收、用户报告和未验证事项。
- 写出已知问题、明确不支持的系统/宿主/硬件范围、分发来源与地区可达性边界。
- 发布后从远端重新下载或读取每个资产的大小与 SHA-256，与本地清单逐项比对。

## 发布顺序

1. 根据实际兼容性和项目版本约定确定 SemVer；任务书/里程碑名称不自动决定包版本。
2. 修改 `package.json`，建立 `CHANGELOG.md` 条目与完整版本说明。
3. 运行 `npm run verify:release-notes`，完成适用的类型检查、自动化测试、构建和目标设备验收。
4. 在版本说明中锁定最终源码 SHA、构建配置、文件清单、哈希和验证状态；未完成项写成限制，不写成通过。
5. 生成候选包并复验资产，审查源码、包内文件、隐私和许可边界。
6. 合并后创建同版本 tag 和 GitHub Release，上传说明、资产与 SHA-256 清单。
7. 逐个复核 Release 远端资产；更新说明、README、CHANGELOG 和任务书状态，记录复核结果。

## 版本说明模板

复制到 `docs/RELEASE-NOTES-vX.Y.Z.md` 后，删除提示文字并填入证据。不要留空字段。

```markdown
# Clawd Desktop X.Y.Z

状态：候选 / 已发布  
发布日期：YYYY-MM-DD 或“未发布”  
基线版本：X.Y.Z  
源码提交：完整 Git SHA  
目标平台：Windows x64 / Codex 宿主范围 / 其他

## 新增
- 功能、用户可见效果、适用范围。

## 调整
- 行为变化及其对现有用户的影响。

## 修复
- 修复的问题、触发条件及回归验证。

## 安全与隐私
- 权限、联网、数据处理、依赖或漏洞变化；没有变化时写“无”。

## 兼容性与升级
- 配置迁移、兼容边界、安装/更新步骤、回退方式。

## 验证范围
- 自动化与精确 SHA CI：结果、运行环境和链接/记录。
- 人工验收：设备、场景、日期；没有独立证据时说明证据来源。
- 未验证范围：明确列出。

## 已知限制
- 当前已知缺陷、不支持范围、服务/地区可达性边界。

## 发布文件与校验
| 文件 | 类型 | 大小（bytes） | SHA-256 |
| --- | --- | ---: | --- |

发布 manifest 在构建时生成，包含确切源码 SHA 与资产哈希；不要在源码文件中手工预填提交哈希，因为这会改变提交自身。manifest 的自身 SHA 由旁边的 `SHA256SUMS.txt` 记录，避免递归自校验。

## 分发与回退
- 正式来源、备用来源、下载限制和回退步骤。
```
